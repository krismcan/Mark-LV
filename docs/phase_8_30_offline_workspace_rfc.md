## 1. User-observable goal and non-goals
A person explicitly starts one normal Nayeon desktop window and can navigate Conversation → Settings → Connection availability → Conversation. Conversation is clearly labelled OFFLINE PREVIEW and never invokes a model, resolver, action bridge, Notepad or permission workflow. Settings permits editing the assistant display name, wake name and optional user display name, reviewing pending changes, cancelling and expressly pressing Save; the displayed name updates only on verified successful save. Subsequent explicit start reads the saved profile if it is valid. This is real bounded local presentation functionality, not a simulated backend, but **does not provide intelligent chat, live provider verification, key management, recovery, computer automation or consent to other actions**. Connection page must display “Not observed; connection operations unavailable in this prototype”; no false READY, fake observations presented as live, or fake setup journey.
The existing --notepad opt-in, all Phase 6 computer-control boundaries, first-run Tk management/host contracts, Phase 8.29 test-owned harness and all historical tags are unchanged. Never wire tests.* into the shipped app.

## 2. Trusted bootstrap and permitted product effect contract
A real local presentation-profile write **is permitted in 8.30 only after an exact human Save on the currently active Settings view**. Test and smoke runs MUST use only temp owned profile roots and fake/blocked provider, credential and computer effects. Real credentials, WinCred, provider calls, SDK construction, native onboarding mutex acquisition, unexpected process spawning and model actions remain prohibited.
The profile destination is one fixed application-private presentation JSON location derived by trusted bootstrap from the verified current Windows user LOCALAPPDATA, under a fixed Nayeon-owned child directory and filename, never from model messages, displayed names, imported configuration, arbitrary cwd or an existing provider/credential path. No access to secrets or credential metadata. Before any path use: require an absolute existing native trusted per-user base directory; reject ambiguous env, reparse/junction/symlink path components, nonregular existing leaf, unsafe permissions and unowned/conflicting target with a bounded user-visible failure. Never auto-migrate, scan or overwrite another config. Start must not create directories/files or acquire a lock; if storage is missing show default presentation values with a clearly unsaved state. Do not silently treat an invalid existing profile as absent. The Settings entry may read only this bounded presentation profile, not a credential source.
On *explicit Save*, the app may create its own missing private child directory only after validating its per-user parent and target. Scope any such creation to the single fixed Nayeon profile child; fail closed on pre-existing conflicting/reparse path. An application-local exclusive profile write guard is required: serialize its own active UI Save and use a bounded OS-level file lock on a fixed sidecar lock file, acquired only on Save and reliably released on every exception, close or crash. This is **not** the forbidden Windows onboarding named mutex. While holding the guard, re-read and validate the current stored profile and compare with the document/version observed at edit start. Refuse stale/conflicting edits rather than last-writer-wins; show “Profile changed elsewhere; reload before saving.” Do not weaken existing typed document validation, existing atomic file store or its failure behavior. The lock is cooperative and cannot prevent rogue external writers; do not claim universal concurrency safety. If secure lock or path proof is infeasible in the limited phase scope, STOP and return RFC HOLD rather than silently saving.
The UI never writes during typing, cancel, close, initial load, failed validation or Save-preview, and never displays a success until stored bytes have been reread and typed verified. File write uncertainty yields failure and fresh reload, not success. No implicit Save on exit. Do not log profile values, user path, sensitive env or full exception representations.

## 3. Trust, ownership and lifecycle
One Tk root and trusted workspace owner. Navigation creates only the chosen view and disposes its callbacks before displaying a replacement. Drafts, SAVE confirmation and path/service state are bound to exact active Settings instance and owning root; a stale/destroyed/reentrant view must never perform a save or update current state. Save and dismiss buttons are disabled during transactional write; duplicate/after-close signals fail closed. Cleanup is owner-only and exception-safe, with no orphan windows/background tasks. Settings selection is explicit; text typed into Conversation cannot navigate or approve settings. Renaming display/wake/user names is a presentation-only projection, never a trusted capability, consent, audit, policy or application identity. Preserve existing validation bounds and avoid accidentally showing secret candidates or local paths.
No provider/backend/recovery composition on startup, navigation, settings preview, Save or teardown. Default offline mode stays visible throughout. Do not import Phase 8.29 fake harness in product.

## 7. Concrete Windows profile owner protocol (revision after independent RFC HOLD)

These normative choices resolve the underdefined profile path and transaction **for architecture review only**. They do not claim existing code already implements them. Production supports Windows only; unsupported OS, missing trusted known folder, owner/ACL ambiguity or missing Win32 primitives is a bounded disabled-Settings result, not an unsafe fallback.

- **Literal destination:** child directory `Nayeon\Presentation` beneath current-user `FOLDERID_LocalAppData` as returned by Windows `SHGetKnownFolderPath` (not `LOCALAPPDATA` text, home or cwd). Profile leaf `presentation.v1.json`. Persistent cooperative lock sidecar `presentation.v1.lock`. No arbitrary path, env override, cloud-sync directory, provider/credential file, mutable UI title or path passed from a model. All supported test boots must inject an exact trusted temporary root through a separate explicit test-only interface before application creation; production does not accept arbitrary profile roots.
- **Owner and DACL:** obtain caller token user SID from Windows; accept only actual local-current-user-owned private child/profile/sidecar, with DACL granting write/delete only to that user, SYSTEM and Administrators; reject generic user/Everyone/Authenticated Users write/delete, inherited broad grants, inability to read the security descriptor, hard-linked existing leaf, nonregular/device targets, and symlink/mount-point/reparse targets or ancestors. Parent known folder must be owned/controlled by user according to local Windows profile policy. New child is created atomically with an explicit protected security descriptor, not created publicly then tightened. New sidecar is created within protected child with restricted descriptor only after human Save; never delete the sidecar after releasing the lock.
- **Identity and containment:** use trusted Windows file-handle APIs (not only `Path.resolve`/stat) to open the known-folder chain and private child with `FILE_FLAG_BACKUP_SEMANTICS` and no `FILE_SHARE_DELETE`, with reparse-tag/volume/unique-file identity and security descriptor checked **on the opened handles**; hold the directory handles until load/replace/readback/cleanup completes. Verify stable child/ancestor identity after each stage. The chosen security-sharing mode must be verified in isolated Windows temp tests to prevent directory substitution while preserving the unchanged store's same-directory temporary-file creation and `os.replace`. Reject any guard acquisition failure; never silently downgrade to ordinary pathname checks. This is a bounded accidental/cooperating-process integrity model, **not** protection against privileged malware or malicious same-user arbitrary code; reparse/path races beyond this enforceable contract remain a STOP, not a claimed success.
- **Sidecar lock:** open fixed sidecar handle with verified owner, DACL, identity and reparse-free regular-file status; acquire `LockFileEx` on its fixed byte range with `LOCKFILE_EXCLUSIVE_LOCK|LOCKFILE_FAIL_IMMEDIATELY`. One process/view Save at a time, with a single immediate failure/brief bounded retry specified by the implementation (never an unbounded spin). Keep sidecar file persistent. Recheck opened handle/file identity and DACL after acquisition. Hold lock and private directory handles through all reads, replacement verification and cleanup; release via `UnlockFileEx` and handle close in `finally`; release uncertainty is a hard SAVE HOLD. Process death unlocks the kernel lock; it does not guarantee temporary-file cleanup, directory sync or power-loss durability.
- **Fresh compare-and-verify transaction:** validate exact current owning root/view, typed draft and separate human-reviewed Save intent *before any profile directory/lock file creation*. Lock. Load fresh from disk using a separately initialized `PresentationConfigurationFileStore`/`PresentationConfigurationService` under the guard; never trust an earlier cached `service.current`. Compare an edit-start token defined as `ABSENT` or `PRESENT` plus SHA-256 and byte count of the original bounded on-disk JSON bytes, together with successful strict document parsing; an absent profile is **not** equivalent to an existing default document. Recheck root/view/generation after all potentially reentrant guard/load/clock dependencies and immediately before write. A changed token refuses Save and directs explicit reload/review. An external ABA change restoring identical bytes is not detected; record this limit, do not claim global CAS. For `ABSENT` at session entry, once Save begins, absent-to-present is a conflict.
- **Publication:** call the existing service's `replace(document)` once under the established owner/lock. Its cached current value is **not proof** of persisted success. Reopen and parse the file in a fresh independent store under lock, compare full immutable typed document (not only names) to the requested document, and verify stable destination identity. Only then publish new UI identity/success. If replace, fsync, cleanup, re-open, typed readback or guard release fails, report `storage may have changed; unverified`, invalidate the edit instance and require a new explicit load and human review. No silent retry or rollback of an uncertain write. Do not log paths, profile contents or private exceptions.
- **Constrained threat model:** only the application's own cooperating instances are serialized by the sidecar. Untrusted local malicious processes sharing/overriding the caller's Windows account can interfere and cannot be safely contained by this app; do not advertise a malicious same-user security boundary. Failure of directory-handle compatibility, actual DACL restriction, profile ownership, or lock/readback proof must be reported as RFC/implementation HOLD before product activation. A narrower first milestone may be an inactive Settings UI until the storage owner is independently verified, but it must never be called completed persistence.

## 13. 16 October 2026 — storage cleanup-observability contract reconciliation (PROPOSED for renewed independent review)

**Superseding correction to the impossible absolute-cleanup promise in §2, §5 A3, §7 and any earlier absolute cleanup wording:** The unchanged, immutable `PresentationConfigurationFileStore.save` deliberately suppresses some temporary-file `unlink` exceptions in its `finally` block.
