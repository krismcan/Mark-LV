# Phase 8 — BYOK trusted first-run journey, fake-only Increment A

Design date: 24 October 2026. This is the first *existing Phase 8 Secure Secrets & BYOK Onboarding* integration increment; it is not a new architecture phase and does not define a product feature named "8.38".

## What this increment actually introduces
The new TrustedFirstRunConnectionOwner in nayeon/desktop_alpha/first_run_connection_owner.py wraps one exact ALREADY CONSTRUCTED CooperativeOnboardingCoordinator. It binds a root, application, pane, journey and generation to a creator-thread-only, single-use UI owner token and ticket. Its sole operations are explicit start, request, confirm, cancel and permanent close/reset. Every dependency may be reentrant, so invalidating a journey during a busy request/approval immediately revokes the candidate's local authority and defers exact owner-only cleanup until the in-flight callback returns.

The constructor imports no provider/client, WindowsCredentialBackend, Tk, filesystem or OS effect adapters. It does not inspect the coordinator's pooled recovery state, construct the coordinator, call for_path, create or alter non-secret metadata, contact OpenAI or access the native Windows Credential Manager. Physical user-click provenance is not proved by a boolean; only a future separately reviewed trusted Tk host may pass explicitly_approved. The new module is not reachable from the default desktop application. In particular, its presence does NOT make the current Connection page functional.

## Why inject a previously constructed coordinator
The existing TrustedOnboardingRecoveryController.for_path shares controllers per canonical metadata path. A conflicting observer in an already-owned tenure can poison its READY state. Creating another coordinator when constructing a new pane would risk disturbing an earlier session. Therefore construction is strictly pure, exact coordinator type checked first, and no pool access occurs until an explicit UI start. A different journey cannot adopt the existing owner token. A production composition factory for real WinCred/validator requires separate security review and is outside this fake-only increment.

## Safe request and response contract
- A user-triggered start claims one UI window owner token on the coordinator's recovery controller; failed/stale claims cannot grant READY or reuse another owner.
- A request only asks the coordinator to issue its native, one-use human-UI ticket; the new owner cannot synthesize the coordinator permit. Stale or reentrantly cancelled tickets are rejected by the same owner. A PENDING outcome is never returned without a live, exact review.
- Confirmation requires same context/ticket, correct creator thread and explicit approval; CONNECT/REPLACE accept an opaque candidate in the UI owner while the existing trusted credential-operation host alone enforces exact SecretValue before storage or validator effects; DELETE additionally requires a distinct acknowledgement, is blocked when a candidate is supplied, and uses the existing coordinator. All CONNECT/REPLACE paths may validate a candidate BEFORE storage when a real validator is supplied; **future real UI must disclose that an external provider request and possible credential storage may occur**. There is no real validator in this increment.
- Results use existing CoordinationReceipt and the invariant requires_reobservation=true, confirms_transaction=false. Never claim a durable cross-store transaction, usable key, valid entitlement or actual connection from a submitted/valid-looking intermediate result. On uncertain effect or navigation during approval, return INDETERMINATE and retain fail-closed state for explicit reconciliation.
- Cancel accepts only the currently owned review object; close invalidates immediately, then rejects only the owning UI ticket, closes the exact tenure, and refuses retries if release is uncertain. A second window must start a fresh human reconciliation with its own owner, not inherit READY from a previous owner's expired admission.
- The owner never saves secrets or metadata by itself. Its fake tests inject prior existing fake backend, fake validator and temporary metadata path plus fake same-process mutex. All real WinCred and API calls are forbidden in tests.
