## C. Proposed user journey and state contract

1. Launch an explicitly labelled **SIMULATED ONBOARDING / NO REAL KEYS** test entry point; import/construct must have no provider, native credential, key mutation, journal transition or approval side effect. Use one Tk interpreter with explicit human-driven navigation.
2. Read-only status/inspection displays fixed nonsecret state. A stale READY or absent marker never implies fresh session admission.
3. If recovery is required, user explicitly opens recovery child, reviews nonsecret journal + typed metadata + credential-presence evidence, and separately approves exact fingerprint within timeout. Closing a child cannot close or revoke the owning management window's tenure.
4. User selects metadata SAVE or CLEAR, or credential CONNECT/REPLACE/REMOVE, and receives an exact one-use operation review bound to owner, ticket, fingerprint, generation/epoch and expiry. Metadata CLEAR and credential REMOVE retain separate explicit destructive acknowledgments.
5. The second human approval callback invokes **only** existing TrustedMetadataCommitHost or CooperativeOnboardingCoordinator methods; do not call the backend or persistence writer directly from new composition code.
6. The existing controller writes/flushes/fsyncs/closes/reopens/rereads an IN_FLIGHT journal record before any fake effect. A missing/unverified journal or native release failure blocks further admission. Failures never trigger automatic effect retry.
7. Re-observe and display a conservative, fixed nonsecret result: metadata requires typed poststate reread; fake credential CONNECT/REPLACE remain uncertain without exact key-value verification even when the fake backend returns success; REMOVE follows existing independent absence rules.
8. On close, external root destruction or reentrant callback, exact owning management panel performs idempotent owner-scoped cleanup, deferring if busy. Old callbacks, tickets and child windows cannot affect a successor session. New session requires fresh reconciliation.

No keys, synthetic candidate literals, owner tokens, private paths or journal secrets may appear in UI status, test logs or review artifacts. Best-effort masked-entry clear is not memory zeroisation.
